# Release compatibility and version impact

Status: implemented as a manual developer command.

## Problem and goal

Tommy wants to detect wire compatibility changes and use that evidence when choosing a SemVer version. He clarified: “I'm thinking that merely having some kind of test command that would let me know what kind of version bump might be required would allow me to decide how to proceed and I can figure out automating things more later”. A standalone manually invoked test command with explained bump guidance satisfies this requirement. Required release enforcement and recorded version-decision approvals are not part of the accepted scope. Tommy retains the versioning decision; automation can be considered later.

## Manual compatibility and version-impact command

The command is useful without any release pipeline. Later feature work can run it manually to inform its compatibility and versioning decisions.

- Compare against immutable, identified Trailboss release artifacts, not freshly generated candidate fixtures. Record source revision, product identity and versions, binary/consumer/producer digests, endpoint generation and codec names. The initial baseline is the deployed, untagged `de20c469` build, not a formal GitHub release. Its installed binary SHA-256 is `718444cbe83522f436c1872fbbf4efa055dae67533aeaa5a7d688618c4f83502`. `tests/fixtures/release-de20c469/inventory.json` now pins the original schema, independent consumer, ordered wire/widget/endpoint declarations, product source and deployment-manifest digest. Original producer bytes are pinned by that manifest's digests; inherited producers' individual source revisions remain unverified and must not be inferred from the Core revision. Do not invent a release tag or substitute upstream Herdr distribution metadata.
- Exercise retained clients and independent API/plugin consumers against a real isolated candidate Core. Compare the released API schema and binary/widget contracts as well as the exercised behavior. Current-type round trips and schema freshness alone are insufficient. Preserve original baseline artifacts; a missing, changed or unidentified required artifact is a failure.
- Report compatible additions, incompatible changes and incomplete evidence separately, with the exact compared revisions/digests, affected contract, client/Core direction and observed result. Identify which graphics, popup and optional codecs have actually been exercised. A plain-PTY consumer does not establish those guarantees. The initial required direction is retained client against candidate Core; additional supported pairings must be stated rather than inferred.
- Report likely SemVer impact with the contract difference and supporting evidence: compatible public additions suggest minor and incompatible stable public contracts suggest major. No detected public contract change may permit patch for compatible fixes, but cannot classify unrelated or unexercised changes. Explain uncertainty rather than inventing a recommendation. For the current 0.x versions, identify compatibility impact and explain that the bump depends on the selected pre-1.0 policy; do not silently adopt one. Keep product SemVer, private protocol 22, endpoint generation 1 and codec names separate. Tommy chooses the version and how to proceed; there is no decision-file requirement.
- The existing endpoint contract retains generation 1 except for security retirement. New functionality must use negotiated optional capabilities or a new named codec while keeping the supported V1 path. The report must explain that a package/private-protocol bump does not itself restore an incompatible public payload. Strict widget consumers must receive their supported vocabulary.
- Provide one documented manual test command with useful output and exit status. Missing or invalid baseline evidence is a test failure, not permission to claim compatibility. The command does not change versions, create tags, publish, enforce releases or require CI configuration. Release automation is explicitly outside this task and is not a prerequisite for building it.

The public verification boundaries are the manual command's output/exit status and retained clients/consumers interacting with real owned Cores/PTYs. Reports provide bounded evidence, not a claim that finite probes detect every semantic incompatibility or determine the correct version automatically. No general SemVer policy is adopted.

The command is implemented by `tests/support/release_compatibility.py`; the documented invocation and reproducible actual-Core fixture recipes are in the README. All nine scenarios in `features/release-compatibility.feature` earned failing behavior, green, meaningful outside-candidate mutation and restored-green evidence, including retained native render/input/detach with original shell PID/start/PTY identity, the independent released consumer, actual unchanged-schema action failure, and real old/new codec negotiation. Source-only API/layout/widget changes are reported as structural evidence or emission risks, not fabricated runtime failures. Graphics, popup and optional delta/reuse/scroll compatibility remain unverified. No release pipeline or general pre-1.0 policy was adopted.
