# Guarded Android conversations and at-most-once automatic playback

Status: contract with an unverified implementation candidate, 2026-10-28. This document owns the code-local contract. The source feature's interview, Technical Spec and delivery plan remain in the original Android workstream; this bounded Core forward-port does not copy them or claim their acceptance scenarios are complete. This candidate is based on deployed r11 identity recovery. Compilation and runtime evidence must be recorded separately; no daily activation or agent restart is authorized by this document.

## Task 1.1 implementation mapping

The subsequently authorized native-phone build adds a candidate Core/reporter implementation of this contract; this is not runtime acceptance evidence and does not mark plan scenarios complete. Reporter version 17 introduced the native OMP `ctx.conversationControl.version === 1` seam. Its synchronous `snapshot()` returns `{conversation_id, reset_entry_id, context_epoch, work:{state,fence}}`. Native `submit({expected_context,context_epoch,text})` and `abort({expected_context,context_epoch,work_fence})` own atomic admission and abort settlement, including desktop admissions. For native-phone capabilities, the reporter never substitutes `sendUserMessage` or `ctx.abort` for this seam.

All four public methods use the existing envelope: success is `{id,result:{type:"agent_conversation",result:payload}}`; error is `{id,error:{code,message,reason,invocation,input_id?}}`. `invocation` is authoritative only when explicitly `not_started`; absent/malformed replies and transport loss remain unknown. Submit and input-status payloads use `status` (`dispatching`, `accepted_by_reporter`, `rejected_before_dispatch`, `unknown`); acceptance includes a process-local opaque UUID string `receipt`, not a native journal entry or answer ID. Abort payloads use `status:"acknowledged"|"not_working"`; guard failures use the error envelope. Existing desktop `agent.chat_submit` and `agent.turn_abort` shapes remain unchanged.

Cursor internals are reporter-private. They retain a canonical binding digest, reporter/context epochs, captured tip, scanned entry ID, fragment byte offset and history/live phase. The digest keeps maximum-length native IDs within the 2,048-byte cursor budget; it is not an authorization credential. Initial display history is a tail of up to 64 native entries, with a separate live baseline at the captured tip. Pages scan at most 4,096 native entries; hidden-only pages still progress. Core and reporter both bound frames; reporter page sizing measures the larger of its control response and the final Core success envelope, including JSON escaping and newline.

## Separate opt-in app bridge

Reporter 18 adds a restricted app profile over the same four public methods and private reporter control socket. It does not satisfy the native-phone contract above or the native-control requirements of tab handoff. It advertises `restricted_app_bridge_v1`, `single_outstanding_v1`, `input_status_v1` and `reply_style_v1`; `restricted_submit_v1` is present only while submission is eligible. Core requires that complete family before forwarding restricted submit. Native clients must continue requiring their native guarded capabilities.

- Opt-in is a regular, non-symlink, single-link, UID-owned mode-0600 file at `/tmp/trailboss-omp-control-<uid>/<pid>.restricted-app.json`, bounded to 4,096 bytes inside the existing UID-owned mode-0700 directory. Its JSON is `{version:1,pid,proc_start_ticks,terminal_id,conversation_id,session_path}`, with start ticks encoded as a decimal string. The reporter validates the process incarnation, exact Core terminal handle and actual session-manager identity/path on each admission. A FIFO, stale marker or mismatched identity cannot enable the bridge.
- `read` with `max_bytes:0` returns binding, epochs, work state and capabilities with `mode:"unchanged"`, `records:[]`, null next/baseline cursors and `has_more:false`. It does not traverse or project conversation history or advance a cursor. Lifecycle hooks and an independent 250 ms timer maintain metadata for opted-in processes, including working agents. A stale metadata-only read can wait at most 750 ms for that independent refresh, then revalidates the grant, binding and context epoch. Identity changes, closure or a cache that does not converge fail closed; no history traversal is moved into the read as a workaround. Positive-budget pagination retains its existing contract.
- Submission rechecks `ctx.isIdle() === true`, no pending messages and no outstanding reservation immediately before the public `sendUserMessage` call. Duplicate/conflict detection is limited to at most 256 reporter-local receipts; missing receipts mean unknown, not proof of nondelivery. An uncertain invocation retains its reservation and must not be automatically replayed. Acceptance is not a model answer or durable/restart-safe exactly-once delivery.
- Known limit: the restricted profile cannot promise that app input never joins a desktop turn. Stock OMP's public `isIdle()` is `!isStreaming`, which excludes a prompt that is admitted but still in pre-turn setup (maintenance wait, extension commands, image normalization, vision description); the admitted-submission state is not visible to extensions. A desktop prompt in that setup window reads as idle, and a desktop prompt submitted during the app prompt's own setup does too, so whichever reaches its turn second is queued as a steer into the other's turn. An `input`-to-settle admission window would not close this: an interactive input that never starts a turn (slash command, handled input, bash, a prompt that bails before `agent_start`) has no observable end, so the window would either lock the app out or rely on a timeout, and it cannot cover the reverse order at all. The app reservation therefore settles on the first settled turn observed after it started, whichever input began that turn.
- The reservation holds desktop session transitions (`session_before_switch`, `_branch`, `_tree` cancel) only after a turn has been observed to start. A public send can return without ever starting a turn (no model or API key, usage preflight, cost cap, Esc during setup); that reservation stays outstanding, without replay, until the next observed settled turn or a session switch, branch, tree or context change releases it, so `/new`, `/resume`, `/fork` and `/tree` stay available as the way out.
- The restricted profile advertises neither native guarded capabilities nor `restricted_abort_v1`; Core still requires `guarded_abort_v1` for abort. App cancellation invalidates the app job and rejects late results. It does not claim queued-input withdrawal or ownership of a later input's work fence.

Activate Core before opt-in enrollment and app pairing. A Core handoff can replace its lifetime-scoped terminal handle while preserving the OMP process and conversation, so an old terminal binding must be refused rather than silently adopted. Installing a reporter file or switching Core does not replace already-loaded extension code. Any necessary targeted agent shutdown/resume requires its own authorization; pairing follows activation and captures the resulting process, terminal and reporter identities.

## Decision and alternatives

Use the private SSH session interface, bounded native-entry reads, identity-guarded wrappers around native input/abort, a read-only input-status operation and one shared Android reducer. Preserve the existing desktop methods and their wire shapes. The new methods must fail closed on older Cores/reporters rather than silently dropping identity guards.

Terminal scraping cannot distinguish an actual answer from tools or hidden reasoning. A second streaming event bus adds replay and ordering machinery without supplying native persistence identity. Matching submitted text to journal text fails for repeated utterances, batches and steering. Durable exactly-once input would require an atomic harness admission/journal contract that has not been established. Retain honest uncertainty instead of adding a second durable input queue. At-most-once automatic playback favors not repeating speech over recovering every interrupted word; explicit repeat remains possible without resending an instruction.

## Current evidence and limits

- The inspected checkout exposes `AgentInfo.terminal_id` separately from workspace/tab/pane locators in `crates/trailboss-runtime/src/api/schema/agents.rs`. `terminal/id.rs` makes this an opaque Core-owned handle, not a value derived from a layout position. Core remains the identity authority across supported moves and handoffs; the shell environment is not that authority.
- `app/api/agent_control.rs` resolves existing chat/abort targets and sends private reporter control requests. The inspected `integration/assets/omp/trailboss-agent-state.ts` declares reporter version 16, uses a 256 KiB chat frame limit, retains at most 256 key-to-`turn_id` entries in memory and invokes `pi.sendUserMessage(...)` before returning acceptance. This checkout is not proof of the installed reporter/Core version or its newer identity recovery.
- [OMP v18.12.6 extension types](https://github.com/can1357/oh-my-pi/blob/v18.12.6/packages/coding-agent/src/extensibility/extensions/types.ts), [session manager](https://github.com/can1357/oh-my-pi/blob/v18.12.6/packages/coding-agent/src/session/session-manager.ts) and [native entries](https://github.com/can1357/oh-my-pi/blob/v18.12.6/packages/coding-agent/src/session/session-entries.ts) expose session ID, leaf ID, branch/entry reads and a `reset_boundary` marker. `/clear` can retain the session ID while changing the conversation context. Native entries visible to the manager are not a promise of an fsync barrier.
- [The versioned input implementation](https://github.com/can1357/oh-my-pi/blob/v18.12.6/packages/coding-agent/src/session/agent-session.ts) documents that omitted `deliverAs` starts an idle turn and steers while streaming. Explicit `deliverAs: "steer"` queues even while idle; do not substitute it unconditionally. Native steering can interrupt a tool batch; it does not promise arbitrary tool preemption. The public extension call returns `void`, not a persisted-user-entry receipt.

These observations establish design inputs only. The exact target runtime must prove guarded admission, native cursor behavior and command delivery in an owned session before exposing the capability. No human agent was prompted, aborted or restarted for this design.

## Binding and compatibility

The phone resolves spoken space/tab names through topology and confirms one eligible agent. It then binds to `(SSH host identity, named Core session, terminal_id, conversation_id, reset_entry_id)`. The last field is the latest native `reset_boundary` on the active branch, or null. Location/name fields are display labels only. Core resolves the terminal's current location and reporter from its owned state; Android never supplies a journal path, PID or inherited shell locator.

Every read after initial selection carries the expected terminal, conversation and reset IDs. Mutations additionally carry a reporter-issued `context_epoch`, which changes on every non-append branch/context switch, including switching away and back. Ordinary appended messages do not change it. This closes the race where the session ID and reset marker remain unchanged during a branch switch. The reporter must enforce the epoch through native admission, not trust a previous Core snapshot. A supported move/rename with the same identity continues automatically. A missing terminal, another conversation, `/clear`, changed branch or ambiguous ownership stops forwarding and speech and requires short spoken confirmation/new selection. No same-named replacement inherits the binding. Core restarts/handoffs may continue only if the same binding and native cursor ancestry are authoritatively recovered; a new reporter supplies a fresh context epoch after that reconciliation.

Use new method names so an older server cannot accept a request after ignoring added guard fields. They reuse existing native input/abort implementation, not PTY input or a second agent loop:

| Proposed method | Required input | Result |
| --- | --- | --- |
| `agent.conversation.read` | Exact `terminal_id`; `expected_context` (conversation/reset pair, null only for initial selection); nullable `cursor`; `max_bytes` | Version, binding, reporter/context epochs, work observation, capabilities, mode, records and cursors |
| `agent.conversation.submit` | Binding; expected reporter/context epochs; client-chosen `input_id`; recognized `text`; `reply_style` (`brief` or `expanded`) | `input_id`, reporter epoch, opaque native receipt, `accepted_by_reporter` |
| `agent.conversation.input_status` | Binding; original reporter epoch; `input_id` | Retained dispatch status/receipt, or `unknown` with reason |
| `agent.conversation.abort` | Binding; expected reporter/context epochs; expected `work_fence` | `acknowledged`, `not_working`, `unavailable` or `failed`; transport loss remains `unknown` |

`read` returns `contract_version: 1` and explicit support for guarded submit, input-status lookup, guarded abort and per-input reply style. Android must require the needed capabilities before forwarding. Unknown methods, mismatched versions, absent native access or unproven guarded admission return `structured_unavailable`; no terminal fallback or automatic reporter restart. Existing `agent.chat.submit` and `agent.turn.abort` clients remain unchanged, but the Android client must not fall back to their unguarded shapes.

A reporter epoch is a fresh process/extension-instance identifier, not a conversation ID. It scopes receipts and admission capabilities. A restart can preserve the conversation while invalidating old receipts. An old-epoch submit/abort must be rejected before invocation. Core must validate support before forwarding, and the reporter must reject unrecognized operations without invoking input/abort.

All four methods use the session interface's existing request ID and success/error envelope. A submit success echoes `input_id` and its admitted binding/epochs. A structured rejection carries `input_id` when supplied, a stable `reason` and `invocation: "not_started"` only when the adapter can prove it. Reasons include `binding_mismatch`, `context_changed`, `reporter_changed`, `work_changed`, `idempotency_conflict`, `capacity_exhausted`, `invalid_params` and `structured_unavailable`. Once invocation may have started, return `invocation: "unknown"` and preserve uncertainty. Missing/malformed responses and transport errors always map to unknown; a generic RPC error is not proof of nondelivery.

Read responses carry `work: {state, fence}`, sampled by the reporter with the snapshot. State is `working`, `not_working` or `unknown`; it becomes unknown immediately on transport loss. A fence is available only when the harness can identify both its work generation and all subsequent input admissions, including desktop inputs. It changes on a new run or a newer admitted instruction. Abort must atomically compare this fence at actual native invocation and reject a stale one. A read-before-abort comparison in Core is insufficient. New admissions must not run through a still-unsettled native abort. If the harness cannot supply that ordering/fence, guarded abort is unavailable; do not advertise it or claim that a delayed cancel cannot touch newer work. Neither fence support nor atomic context admission is established by the inspected public extension interface.

Submit must validate both the incoming request and the final control content after attaching the fixed voice policy. The final text is at most 128 KiB of UTF-8; the complete encoded control request, including guards, policy, JSON escaping and newline, is at most 256 KiB. Oversize is `request_too_large` with `invocation: "not_started"` only if validation occurred before native invocation. Never truncate recognized instructions. A client-detected oversize before write stays unsent; failure after a transport write may have happened remains unknown unless a matching structured rejection proves otherwise. Receipt/error responses are bounded to 65,536 bytes. These stricter byte limits are compatible with the inspected control path; they are not speech-performance measurements.

## Read schema and cursor rules

A read response has the following logical shape. Names are proposed wire fields, not implemented schema declarations:

```json
{
  "contract_version": 1,
  "binding": {
    "terminal_id": "term_example",
    "conversation_id": "native-session-id",
    "reset_entry_id": null
  },
  "reporter_epoch": "reporter-instance-id",
  "context_epoch": "active-context-generation",
  "work": {"state": "working", "fence": "native-work-and-admission-fence"},
  "capabilities": ["guarded_submit_v1", "input_status_v1", "guarded_abort_v1", "reply_style_v1"],
  "mode": "delta",
  "reset_reason": null,
  "snapshot_tip_id": "native-entry-at-capture",
  "records": [{
    "entry_id": "native-message-id",
    "parent_id": "native-parent-id",
    "role": "assistant",
    "stop_reason": "stop",
    "has_tool_calls": false,
    "text_total_bytes": 26,
    "text_offset_bytes": 0,
    "text": "The actual assistant text.",
    "entry_end": true
  }],
  "next_cursor": "opaque-versioned-position",
  "baseline_cursor": null,
  "has_more": false
}
```

1. A null initial cursor captures a bounded tail snapshot for display and returns a separate `baseline_cursor` positioned at the captured current tip. Store that live baseline before activating speech. Initial history is silent, even if it needs multiple pages. Its `next_cursor` continues only that pinned history; Android starts live reads from `baseline_cursor`, not from the last displayed historical record. Live reads take priority over optional history loading. A null native tip is a valid empty-session baseline. Non-initial responses set `baseline_cursor` to null.
2. A cursor carries binding, issuing reporter/context epochs, captured branch tip, scanned native entry position, history/live phase and text-fragment offset. It is opaque to Android, validated by the reporter and not an authorization token. Parent IDs may refer to filtered-out entries. Scan positions advance over filtered entries too; an all-tool interval returns a progressed cursor even with no visible records.
3. `snapshot` pages are historical; `delta` pages follow a live cursor; `unchanged` advances nothing; `reset` invalidates a prior position. Pinned pages are chronological through the captured tip. While `has_more` is true, `next_cursor` advances within that snapshot. The final page's cursor is positioned at its captured tip; the next read captures a newer tip and returns its appended suffix. `unchanged` retains the same live position. Thus the client never compares opaque IDs lexically or guesses whether a history record is new. Later appends cannot change an in-progress page sequence. With the same reporter epoch, any context-epoch mismatch forces `reset/branch_changed`, even after switching away and back to the same tip. Android compares these epochs before accepting records or speech, not only before mutations.
4. When ancestry is lost, return `reset` with `branch_changed` or `history_unavailable`, discard partial text and queued speech, and obtain a fresh silent baseline. Branch/context change needs spoken confirmation before forwarding again. After a reporter restart, reconstruct only when terminal/conversation/reset IDs still match and the saved captured tip and scan position are on the current branch, with valid fragment offsets. This explicit exception reissues the same position under the new reporter/context epochs; Android invalidates old callbacks and adopts those epochs without replay or another tap. Otherwise reset and require selection/confirmation. A mere cache expiry with valid native position on the same reporter/context is also reconstructable without asking Tommy. Do not infer ancestry from timestamps. Refresh epochs before any mutation.
5. Default `max_bytes` is 65,536; accept 4,096–65,536. Measure the entire encoded UTF-8 JSON response including escaping and newline, below the existing 256 KiB reporter frame. Bound IDs to 256 UTF-8 bytes and opaque cursors to 2,048 ASCII bytes; reject invalid/oversized values. If mandatory metadata cannot fit the requested budget, return a bounded `page_budget_too_small` error with no cursor advancement. Split large text records only at UTF-8 boundaries, reporting total decoded UTF-8 size, increasing offsets and `entry_end`; never silently truncate. Total size and `has_tool_calls` are consistent on every fragment. Unknown tool-call metadata means no speech. A total above 1 MiB makes the entry unplayable immediately: release/avoid its playback assembly, send fragments to a bounded, virtualized transcript window, and keep paginating through `entry_end` to later entries. Discarded display chunks remain re-readable via their saved page cursors, not retained indefinitely in memory.

Only normal user text and assistant text cross this read seam. Exclude tool messages, tool-call arguments, thinking blocks, custom/agent-synthetic user injections and attachment/path metadata. Ordinary text containing a filename or URL remains actual message text; do not pretend to detect or redact every local path inside prose. Preserve assistant stop reasons; unknown reasons fail closed for speech. Never resolve an artifact/blob URL merely because it occurs in text. A message with no visible text need not produce a text record, but still advances the scan position. `/clear` starts after its reset marker, not before it; compaction summaries are not assistant replies and do not by themselves change native conversation identity.

Speak only a fully assembled assistant entry from live `delta` pages with stop reason `stop` and native-derived `has_tool_calls: false`. Historical snapshot pages and unknown/mixed content are never eligible. Client playback-generation checks below apply as well. Other assistant records can be displayed with incomplete/error status, never spoken as completed answers. Do not speak an SSE fragment, `message_end` notification or generic Working/Idle transition as an answer. A reply observation updates conversation state, not a per-input “answered” flag.

Poll no more often than once per second while voice is active or the phone conversation is foreground, with one live read in flight. Activation, completed input dispatch and transport restoration may bypass that interval for an immediate refresh. Stop polling when neither condition holds. This is an initial engineering parameter, not measured responsiveness. Cache native identity/branch projection; unchanged polls must not serialize history, and append reads should traverse only the new suffix using native IDs. Bound initial/reset indexing work away from the Core UI loop. Recheck binding/context around snapshot assembly; if they changed, discard that assembly. A concurrent append alone does not invalidate the captured tip's pinned sequence.

## Input receipts and ordering

Generate a fresh `input_id` for each completed deliberate utterance. Keep a local input record before writing it. Persist its ID, binding and dispatch state, not a duplicate full transcript; recognized pending text may remain in app-private memory. Raw audio is not retained. Keep this recovery metadata app-private and out of automatic backup. Losing volatile draft text on process death does not authorize recreating or resending it.

| Input state | Evidence and permitted transition |
| --- | --- |
| `draft` | Completed text not dispatched; unavailable transport is visibly not sent, never silently queued for later reconnection. |
| `dispatching` | Journal this state before transport write. A crash from here means unknown, even if the write may not have happened. |
| `accepted_by_reporter` | Matching receipt proves that the reporter accepted/invoked the native submission path, not provider consumption, persisted user-entry association or completion. |
| `rejected_before_dispatch` | A guard/capability/validation rejection proved no native invocation. A later user retry is a new deliberate attempt. |
| `outcome_unknown` | Timeout, lost response, restart, evicted receipt, or a failure after invocation began. Never label this definitely failed. |

Use at most 256 process-local receipt/reservation slots, scoped by binding, reporter epoch and `input_id`, with a content/style digest. Reserve the key atomically before invoking native input. Concurrent same-ID requests join that reservation rather than invoke again; different text/style is `idempotency_conflict`. Status lookup returns `dispatching`, `accepted_by_reporter`, `rejected_before_dispatch` or `unknown`, with a receipt only for acceptance. A failure after invocation starts is retained as unknown and never retried under that reservation. Never evict in-progress slots; if all slots are in progress reject new admission as `capacity_exhausted` before invocation. Evict the oldest settled slot when needed. There is no promised retention duration or durable exactly-once guarantee: after eviction/restart an absent key proves nothing, and clients must not automatically retry it. Lookup is read-only. Do not discover a receipt by matching text, timestamps or the next assistant message.

Serialize short native control dispatches in completed-utterance order, not until the provider turn ends. A timeout leaves that input unknown but must not permanently block a later deliberate steering instruction under its own ID. Track each input separately if receipts arrive out of order. A later reply can address several inputs; there is no receipt-to-answer cardinality guarantee.

Once a write may have occurred, reconnect never automatically resubmits it, even under the old key. Say briefly that delivery is uncertain and ask before repeating the instruction. An explicit resend is a new deliberate input and warns that the original may already have run. New instructions remain possible while an earlier input is unknown.

The guarded adapter must preserve the expected conversation/reset through native dispatch, including asynchronous queue admission and a concurrent session switch. Checking only before calling the extension function is not sufficient. Advertise guarded submission only after exact-runtime proof of that invariant; otherwise return `structured_unavailable`. Any needed harness-seam change is implementation work requiring later authorization, not permission to weaken the guard. Use the documented native idle-start/working-steer semantics; do not unconditionally request the explicit idle-queuing `steer` option. No client queue waits for agent completion.

For brief inputs, prepend a fixed, visibly scoped voice-format instruction to that input's text: answer this request with a short actual reply suitable for ten seconds; give detail only if requested; do not apply this format to unrelated desktop requests. `expanded` carries the explicit request for more detail. Do not change global settings/system prompts or install a persistent profile. Keep the original recognized text in the local input view and expose the actual submitted policy text in diagnostics. The policy is an instruction, not a model guarantee; overlong actual output remains a visible failure. Do not infer native entry association by looking for this prefix.

## Shared playback and work state

Keep independent fields for binding/read position, input records, reported agent work state, voice lifecycle and playback. A single `busy` flag would incorrectly equate speaking, waiting for a receipt and agent work. The phone and Auto adapters share these fields and transitions, with one audio owner.

The voice lifecycle is `off`, `active`, `suspended` or `needs_selection`. Explicit begin commits an active voice intent before acquiring audio. Route/transport loss suspends it; same-binding recovery resumes automatically when the service start/restart path, host/session, credentials/state, permissions and focus permit, including verified OS process recreation with surviving active intent. Explicit end stops capture/assistant playback and commits `off` before acknowledging the end; restoration must not reactivate it. One short local end confirmation may follow the committed off transition when the existing route/focus permits, but no agent output or microphone reactivation. Binding/context mismatch commits `needs_selection`. A fresh process never restores capture or speech merely because a route exists: load committed intent, revalidate native ancestry and eligibility, recover input uncertainty, invalidate old callbacks and only then resume active intent without another tap. Missing/corrupt recovery state or storage failure fails closed. Never restore an old audio queue or partial recording. No lifecycle event here aborts agent work implicitly. [ADR0009](0009-phone-setup-controls.md) distinguishes ordinary recovery from explicit stop, privacy/force-stop/boot, speech faults and unclassified car stream end; none permits bypassing OS controls.

Use a local playback ledger keyed by binding and native assistant entry ID, independent of the read cursor. Commit an entry's handled claim before TTS; a crash can omit speech but cannot automatically repeat it. Observed entries can be queued, claimed, finished, interrupted, suppressed or unplayable. Atomically persist voice intent, binding/read position, observation-window ID/style/remaining allowance, handled/suppressed IDs and input recovery metadata before dependent effects. Reserve playback allowance before output; an unfinished reservation after a crash consumes its full reserved amount rather than renewing the budget. A completed output can return its unused reservation. Recovery uses saved native positions to continue the unseen suffix without replaying handled entries; unclaimed text associated with a lost in-memory queue is suppressed when encountered. Preserve its IDs or the scanned high-water position so it cannot reappear as new. Explicit repeat reads retained/native text, never resubmits the original instruction. When a newly confirmed selection establishes a fresh silent baseline, old playback metadata may be removed; unresolved input outcomes remain until acknowledged. Do not evict active-session suppression merely to meet a cache cap.

On speech onset, immediately stop playback and invalidate its queued remainder before endpointing. Capture the new utterance; submit after endpointing only if voice and binding still permit it. Maintain separate context, playback and audio-route generations. Reads, fragment assembly, queued text, synthesis and output callbacks carry the relevant generations. Selection/context changes invalidate all three; barge-in/cancel/end invalidate playback; route/transport loss invalidates playback and audio ownership. No stale callback may publish speech or submit partial audio. A context-valid but old-playback-generation read can update the transcript/cursor only if it still extends the current read position; its speech records are suppressed, not re-enqueued. Out-of-order reads never rewind the cursor. On recovery revalidate the same binding and continue from the retained read position with a new playback generation; previously observed old-generation records remain suppressed. Echo suppression/double-talk quality still require phone/car measurements.

Activation creates a local brief observation window with ten seconds of cumulative assistant output, not ten seconds per chunk/page/message. Each finalized non-control voice utterance creates a new local window and suppresses the old queue; it starts brief even if dispatch later fails or stays unknown. A requested `expanded` style upgrades that window only after matching reporter acceptance/status, and only if it is still the latest window. A rejected or unknown detail request stays brief; a late receipt never upgrades a newer window. No receipt attributes an assistant answer to that input: the allowance governs an observation window, not a proven per-input answer. Previously observed entries never move to a new window; newly observed eligible entries belong to the current one even if the agent was already generating them. A new utterance may reset the allowance without proving a new provider turn. Suspension/process recreation preserves the committed allowance and never renews an unfinished reservation. Claim/suppress output at cutoff and report overlong actual generation as a policy failure. Expanded playback stays interruptible. Local end/cancel commands do not renew the allowance.

Explicit cancel uses guarded abort with the current work fence, stops local playback and invalidates queued speech, leaving voice available for the next instruction. Without a current authoritative fence, report cancellation unavailable rather than sending an unguarded abort. A stale fence yields `work_changed` without invocation. Report “cancellation requested” until matching acknowledgement; `not_working` is a no-op, not rollback. Lost acknowledgement is unknown and is not automatically retried. Later submissions can proceed only after the native abort admission/settlement gate permits them; the fence must also reject an original delayed cancel after newer work/input starts. If the runtime cannot enforce this, the guarded capability remains unavailable. Even `acknowledged` means the native abort path accepted the request, not that external effects were undone or all queued work ceased. Observed work state stays separate. Do not use shutdown for cancel; ending listening sends no abort.

## Verification and readiness

Task 1.1 must prove the exact guarded read/submit/status/abort path in an owned agent, including a session/reset change during native admission, old-reporter refusal, two steering inputs, hidden-entry filtering, UTF-8 byte bounds, all-hidden pages, branch change during pagination, `/clear` with unchanged session ID, reporter restart and status lookup without delivery. Compare native journal entries with reads; a receipt alone is not that proof. Guarded cancel must also survive identity change and lost acknowledgement without touching newer work.

Tasks 2.1 and 3.1 must exercise persisted playback claims, stale callbacks, cumulative ten-second cutoff, explicit detail, barge-in without abort, explicit cancel, uncertainty without replay, route handoff and same-binding reconnect. Keep all existing plan scenarios and all three real car routes. A throwaway pure state model can expose contradictions in these rules; it cannot certify OMP admission, actual speech, phone audio or vehicle behavior.

Design checks completed on 2026-10-28: a throwaway pure Python model passed 16 scenario groups covering duplicate reservations, receipt loss/restart, branch/reset admission, delayed cancel fences, eligibility, cumulative cutoff, stale callbacks, expanded-window receipts, UTF-8 frames, cursor progression and persisted active/off recovery. Fresh readers found admission, cursor and persistence gaps; the document was corrected and focused rechecks found no remaining issue in the changed contracts. The JSON example parses and its declared text byte count matches UTF-8. No permanent test/scaffold, production implementation, socket traffic, agent input, microphone or vehicle was exercised by these checks.

Task 1.1 has a Core/reporter candidate, including behavioral consumer tests, but source changes alone do not certify runtime guarantees.
