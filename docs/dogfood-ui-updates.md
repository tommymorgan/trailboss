# Dogfooding UI updates without losing sessions

**Historical investigation, current product Trailboss:** The installed revision-10 `herdr-spike` bundle, binary hash, smoke results and process identities below describe the pre-rename installation, not a current Trailboss deployment. Current source uses `trailboss-plugin.toml` and `target/debug/trailboss`, but retains the original `min_herdr_version` field, `{herdr: "widget_tree", ...}` declaration schema and `HERDR_*` transport/plugin context. Source links follow the renamed tree; product branding does not change the wire contract or upgrade/migrate a running Core.

**Keep the named Core running. Relaunch only the client for renderer changes; explicitly restart the affected producer for declaration changes. A new widget variant such as `Modal` also needs a compatible Core—not just a new client.**

Investigation: 2026-10-12. This is an evidence-backed design recommendation, not an approved deployment plan. No human session, installed package, modal implementation, or deployment was changed. One disposable, isolated Core was used for the producer smoke below; no Cargo command was run.

## Update boundary

| Change | Can retain the running Core and PTYs? | Required update |
| --- | --- | --- |
| Client layout, drawing, hit-testing, menu positioning, input handling using existing API semantics | Yes, provided existing endpoint/declaration contracts remain compatible | Detach/close the client and launch the new client against the **same named session**. |
| Producer labels, composition, fragments, ordering, styling, or action wiring using nodes/actions already supported by Core and client | Yes | Replace the producer artifact and explicitly restart that producer. Clients receive the new declaration live; no client relaunch is necessary unless its renderer also changed. |
| Producer manifest metadata, command, or root | Yes | Re-link the intended root or refresh the installed manifest; reconciliation replaces affected producer generations. Preserve the intended enabled state. |
| New widget enum variant/field, condition, reserved `host:` action, or server API behavior | Not by client/producer replacement alone | Update the Core implementation/schema too. `Node::Modal` is in this category. |
| Ordinary Core stop/restart, incompatible live-handoff state, or lost Core process | Not a guarantee of identical live PTYs/processes | Disk restore is not live-runtime preservation. Unix live handoff is the existing possible upgrade path, but its actual old/new pair must be proven before dogfood use. |

Sources: [client attachment/startup](../src/main.rs#L112-L159), [client declaration consumption](../src/lib.rs#L160-L174), [typed Core declaration parsing](../crates/trailboss-runtime/src/app/api/plugins/ui.rs#L717-L738), [widget validation](../crates/trailboss-runtime/src/protocol/widgets.rs#L126-L207), and [disk restore spawning versus imported-runtime restore](../crates/trailboss-runtime/src/persist/restore.rs#L636-L666).

## Producer lifecycle: what reload actually means

1. **The registry stores installed roots/manifests, not running source-code generations.** Its path is `<config_dir>/plugins.json`, shared across named sessions in that config home—not one registry per session. Registry refresh reloads manifests and compares the resulting `InstalledPluginInfo`; unchanged metadata returns without reconciliation. Editing a script alone therefore does not cause a stream restart. A uniquely named session alone would not isolate plugin registry mutations; the smoke also isolated its config home. Sources: [registry path](../crates/trailboss-runtime/src/persist/plugin_registry.rs#L11-L16), [config directory](../crates/trailboss-runtime/src/config/io.rs#L22-L29), [manifest reload/equality](../crates/trailboss-runtime/src/app/api/plugins/mod.rs#L28-L58).
2. **There is no `plugin reload` CLI command.** Existing commands are `plugin link`, `list`, `enable`, `disable`, and others. A live `plugin link <root>` invalidates that plugin's streams/cache before reconciliation. `plugin enable <id>` does the same even when it was already enabled: it is an available single-call restart of an enabled producer, without a disable interval. `plugin disable` removes its UI and clears its agent-view source; re-enable starts it again. These commands mutate registry state, so do not casually apply them to every session or re-enable an intentionally disabled plugin. Sources: [CLI dispatch](../crates/trailboss-runtime/src/cli/plugin.rs#L20-L44), [registry mutation and link](../crates/trailboss-runtime/src/app/api/plugins/mod.rs#L61-L106), [enable/disable implementation](../crates/trailboss-runtime/src/app/api/plugins/mod.rs#L756-L787), [UI invalidation/reconciliation](../crates/trailboss-runtime/src/app/api/plugins/ui.rs#L99-L188).
3. **Restart cancels only the supervised producer process tree.** Stream lifetime is owned by a stop sender outside `AppState`; cancelling it terminates and reaps the producer. Reconciliation retains streams only while the entry is enabled/eligible and its installed metadata matches. Stream events carry generations, protecting replacement producers against stale output. This is distinct from restarting pane runtimes. Sources: [runtime ownership](../crates/trailboss-runtime/src/app/api/plugins/ui.rs#L45-L58), [reconciliation and generation assignment](../crates/trailboss-runtime/src/app/api/plugins/ui.rs#L112-L188), [generation checks](../crates/trailboss-runtime/src/app/api/plugins/ui.rs#L190-L237), [cancellation and reap](../crates/trailboss-runtime/src/app/api/plugins/ui.rs#L296-L335).
4. **Client relaunch is not a producer-code reload.** Local startup first attaches to the existing Core, spawning one only for missing/refused sockets. It lists plugins and chooses manifests beside the executable when available, otherwise the repository's `plugins` directory. For an already registered canonical root it skips re-linking entirely. A different root is re-linked while preserving `enabled`; absent agent-tree is deliberately not auto-installed. Remote startup delegates producer registration to the remote client bridge, so changing local producer files does not update remote producer artifacts. Sources: [attach versus spawn](../src/main.rs#L112-L151), [default-producer registration](../src/main.rs#L478-L542), [remote bridge callback](../src/main.rs#L49-L54).

## Widget compatibility is not negotiated yet

Core parses producer JSON into the compiled `Declaration`/`Node` types and validates it before forwarding it. `Node` is an internally tagged enum with `deny_unknown_fields`, and `Declaration::validate` accepts only `herdr = "widget_tree"`, version `1`, known nodes/conditions/actions, and bounded structure. The current working source adds `Modal`; the running revision-10 Core described in the assignment predates it. That old executable cannot deserialize `type: "modal"`, including inside a `when` whose condition is false: parsing precedes client-side condition evaluation. Updating the client cannot repair Core's rejection. Sources: [typed enum](../crates/trailboss-runtime/src/protocol/widgets.rs#L34-L94), [declaration validator](../crates/trailboss-runtime/src/protocol/widgets.rs#L115-L207), [Core parser](../crates/trailboss-runtime/src/app/api/plugins/ui.rs#L717-L738).

Unknown-node JSON is a parse error: a streaming producer's reader exits through the error path and its process is terminated. A declaration that parses but fails validation produces an empty UI projection. Neither is a safe compatibility fallback for a stock application composition. Sources: [parser distinction](../crates/trailboss-runtime/src/app/api/plugins/ui.rs#L717-L726), [stream error termination](../crates/trailboss-runtime/src/app/api/plugins/ui.rs#L303-L346).

There are three separate checks, none of which currently establishes support for `Modal`:

- **Endpoint generation/codecs:** the fork client sends generation `1` and V1 snapshot/surface/input/blob codecs. Core checks generation, required codecs, and geometry. Welcome advertises `plugin_ui`, not a widget-language/node feature list. Same-generation attachment can succeed while producer declarations are incompatible. Sources: [client hello](../src/lib.rs#L53-L82), [handshake checks](../crates/trailboss-runtime/src/server/client_transport.rs#L738-L774), [welcome capabilities](../crates/trailboss-runtime/src/protocol/endpoint.rs#L219-L241).
- **Private protocol:** direct-terminal and normal CLI operations enforce private protocol compatibility (`22` in the inspected source). Endpoint compatibility is deliberately independent. The fork's `receive` currently ignores the named endpoint welcome through its default match arm; do not treat attachment as proof of negotiated widget support. Sources: [protocol contract](../crates/trailboss-runtime/src/protocol/wire.rs#L1-L20), [CLI guard](../crates/trailboss-runtime/src/cli.rs#L769-L800), [client receive](../src/lib.rs#L176-L193).
- **Plugin minimum version:** manifest loading compares a semantic Herdr version to the running build. It does not compare package revision, widget schema, supported nodes, or producer/client capabilities. Installed `min_herdr_version = "0.9.0"` therefore does not discriminate revision-10 schema from the modal schema. Sources: [manifest check](../crates/trailboss-runtime/src/app/api/plugins/manifest.rs#L256-L284), [declaration version](../crates/trailboss-runtime/src/protocol/widgets.rs#L126-L130).

The endpoint contract requires unknown enum values to have an `Unknown` fallback; the typed widget enum does not currently have one. The client also deserializes the entire typed `EndpointPluginUi`, so an older client cannot safely consume a declaration containing a newly added node. Future schema changes must address **both** consumer boundaries, not merely keep endpoint generation `1`. Sources: [endpoint evolution contract](../crates/trailboss-runtime/src/protocol/endpoint.rs#L1-L9), [typed endpoint declaration field](../crates/trailboss-runtime/src/protocol/endpoint.rs#L110-L126), [client parse](../src/lib.rs#L160-L174).

## Core upgrades: existing handoff, not a second PTY daemon

An ordinary disk restore uses `TerminalRuntime::spawn_with_initial_history` when there is no imported runtime. It recreates shells/processes from saved state; it does not recover the same PTY FD merely because pane labels/IDs return ([restore branch](../crates/trailboss-runtime/src/persist/restore.rs#L636-L666)). Therefore session-reset workflows are unsuitable for UI dogfooding.

**Do not conclude that every Core update necessarily kills PTYs.** The vendored Unix runtime already implements explicit `server live-handoff --import-exe <path>`. It bypasses the normal CLI protocol guard because handoff is itself an upgrade path. Export pauses readers, captures session/runtime state, duplicates PTY descriptors, starts the replacement executable in import mode, transfers descriptors, waits for readiness/commit, and relinquishes the old runtimes without killing them. Failed pre-commit imports resume the original readers. Clients disconnect and must reconnect; subscriptions/in-flight operations are intentionally not preserved. Sources: [CLI handoff](../crates/trailboss-runtime/src/cli/server.rs#L205-L236), [export/commit/rollback](../crates/trailboss-runtime/src/server/headless/lifecycle.rs#L25-L287), [spawn import](../crates/trailboss-runtime/src/server/handoff.rs#L65-L107), [import dispatch](../crates/trailboss-runtime/src/server/headless/bootstrap.rs#L9-L34), [preserved versus transient state](../crates/trailboss-runtime/src/handoff_runtime.rs#L4-L10).

This path is not automatic on client relaunch or producer reload. Import requires a readable handoff manifest/version, descriptors, restorable runtime state, and readiness; optional expected target version/protocol checks protect against importing the wrong binary ([manifest/import validation](../crates/trailboss-runtime/src/server/handoff.rs#L20-L49), [validation checks](../crates/trailboss-runtime/src/server/handoff.rs#L237-L268)). A breaking import/runtime-state change cannot preserve PTYs through this path until migration support exists. No revision-10→modal live handoff was exercised, and no runtime cutover was attempted. Its safety for that pair remains unverified—not impossible, and not established by the producer smoke.

## Actual isolated smoke

Used the existing `target/debug/herdr-fork`, SHA-256 `11d2ea4ead1361648b96c337e8d09d8c48bf751a205a515c3e6e1c29a5b6101c`; runtime snapshot reported `0.9.3`, private protocol `22`. All HOME/XDG homes and the config path were isolated under an owned temporary directory. Core PID was `2479315`, named session `producer-smoke`, plugin `example.owned-update-smoke`. The producer printed a valid label declaration and remained alive; it recorded each process PID. A small framed generation-1 endpoint observer read only this owned session's declaration projection.

| --- | --- |
| Link initial script | Producer PID `2481510`. |
| Replace script's emitted label A→B; call `plugin.list` with unchanged manifest | PID log remained only `2481510`: source replacement/list did **not** restart it. |

Waiting for a new projection after the manifest-only change timed out because the rendered declaration was unchanged; no changed-projection claim is made for that step. |

Core remained alive throughout. Initial/final pane identity was `w1:p1`, terminal `term_65d9dfafbbe161`. This demonstrates declaration replacement/producer lifecycle independent of the Core; it is **not** a child-PID or PTY-FD identity proof. The separate client-reattach investigation owns that evidence. The owned Core was stopped through its own API, exited `0`, every recorded producer PID was gone, and temporary files were removed. No human pane contents were inspected.

## Smallest durable dogfood design recommendation

1. **Retain the existing long-lived named Core and separate client process.** Make client refresh an attach-only operation for an existing session; never conceal an incompatible attach by stopping/resetting Core. Keep the user's session selection stable. This already matches local attach-before-spawn behavior; no new PTY-owner service is necessary for UI-only work.
2. **Separate producer artifact updates from client relaunch.** Keep an explicit, targeted producer restart step. For an enabled plugin today, `plugin enable <id>` is sufficient; root/artifact generation changes can use re-linking with the existing enabled-state preservation rule. Prefer coherent versioned producer directories over overwriting a running artifact piecemeal. Do not automatically link the latest repository stock producer into an older live Core.
3. **Add one explicit widget-compatibility contract before treating schema evolution as hot-updatable.** Advertise supported widget schema/features from Core and consuming client, require the producer's needed features before replacement, and reject incompatible generations before dropping the working producer. A new `Modal` needs a Core and client that both support it. Keep typed Core validation; silently discarding an unknown modal would erase interaction semantics, not provide compatibility. This is a proposal, not implemented capability negotiation.
4. **Treat Core replacement as a separate, explicitly tested Unix handoff operation.** Use the existing FD handoff rather than adding another daemon or moving validation out of Core just to avoid the modal baseline update. First prove the actual old/new import pair in an owned session with stable child PIDs/PTY behavior, reconnect, and failed-import rollback. Only then plan a human-authorized cutover. Otherwise leave the existing dogfood Core alive and run the incompatible schema in a separate test session.

For the immediate modal change: **client relaunch plus stock-producer restart is insufficient on revision-10 Core.** A compatible Core baseline is required. Routine producer/renderer iterations after that baseline can keep PTYs alive without Core replacement; future server/schema changes still need compatibility-aware handoff, not an assumed reset-free reload.
